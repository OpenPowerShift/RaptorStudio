[[ch-what-if]]
== What Drives Downtime, and What Would Help

*Time: about 45 minutes.*
*New ideas: the Story, downtime attribution, the three criticality indices,
what-if comparison on shared seeds, precision, sensitivity and
the cheapest spare holding.*

=== You will learn

* How to read the answer before the tables: the Story's headline, dots,
  drivers and findings.
* The difference between *what happened* (attribution) and *what a change
  would achieve* (importance and what-if).
* How to stop a batch when the interval is tight enough instead of guessing
  a run count.
* How to see which inputs move the answer, and how many spares to hold.

=== You need

* <<ch-first-model>> through <<ch-sparing>> finished.
* A model with at least one redundant group, so an outage has more than one
  possible cause.

=== Start with the answer

Open the model, run it, and read the **Overview** tab. Below the key-number
cards is the Story, which adds only what the cards do not say:

* when a requirement is set, a **headline** against it and a **dot plot** of
  the per-run values: each dot is one run in a hundred, filled when it met the
  target and hollow when it missed;
* one line naming the top **drivers**, ranked by lost capacity when capacity
  analysis is on and by downtime otherwise, with a link to the **Drivers** tab;
* the **findings** from the Advisor.

The same object is available without the application:

[source,bash]
----
raptor explain VanFlat.rbds --story
raptor explain VanFlat.rbds --story -f json
----

The Story never invents a verdict: without a target it says so, and without
attribution it offers the one action that turns the drivers strip on.

To hand the answer to someone who will not open the model, write the report:
the Story, its charts, how to read each measure and the diagram, as a PDF or
one self-contained HTML file. It is the document File › Export… makes as a PDF report;
add `results` or `data_tables` to `--report-include` for the tables. An AI
assistant uses the MCP tool `export_report`.

The cover always carries the key figures, with or without the tables. Its
*time between outages* is all the working time divided by all the outages,
over every run. Raptor's MTBDE, kept small under it, is an average of each
run's own value; a run that never went down counts as its whole length, so
when outages are rare MTBDE is only a floor (">8,760" for one-year runs)
and the pooled figure can be a hundred times longer. With fewer than ten
outages the figure is rounded and marked as too few to be firm.

[source,bash]
----
raptor explain VanFlat.rbds --report VanFlat.pdf
raptor explain VanFlat.rbds --report VanFlat.html --report-include diagram,story,results
----

=== What caused the downtime

Attribution replays the event log; it does not change a result. For every
system outage it records the element whose state change started it and what
the time was spent on: hands-on repair, waiting for a spare, waiting for
people or equipment, logistics, planned maintenance, or being held by
another element.

Three indices answer three different questions:

[cols="2,4,4",options="header"]
|===
|Index |Question |Caveat

|DTCI
|What share of the system's *downtime* did this element start?
|Describes this design; says nothing about what a change would achieve.

|DECI
|What share of downing *events* did it start?
|Counts events, so a very short outage weighs the same as a long one.

|FCI
|What share of *failure-started* outages did it start?
|Planned maintenance is excluded, as it should be.
|===

Open the **Drivers** tab for the full table with error bars and the cause
split. The command line prints the same numbers:

[source,bash]
----
raptor explain VanFlat.rbds --top 8
----

For a phased model the same replay also splits the downtime by mission
phase: how long the system spent in each phase, how long it was down there,
the phase's availability (down time over time in the phase, pooled over the
runs) and the element that started most of that downtime. An outage that
runs from one phase into the next is split at the phase change, and each
part is charged to the element that started the outage. `raptor explain`
prints a **Downtime by phase** table, the Charts tab has a **Downtime by
phase** chart and a **Phase by cause** heatmap (`phase-downtime` and
`phase-cause-heatmap` from the command line and MCP) and the
exported tables include `results.phase_downtime`.

A model with hierarchies also gets each hierarchy's share of the downtime:
the outages started by anything inside it, at any depth. `raptor explain`
prints it as a **By hierarchy** table, indented by depth, and
`downtime_drivers` returns it as `hierarchies`. The share is worked out from
the hierarchy's own downtime in each run, so its ± is its own. Adding up the
± of the elements inside would overstate it, because those elements fail
together often enough that their errors are not independent. On the canvas,
the Σ badge on a collapsed hierarchy's oval shows the same figure, and its
tooltip gives that range.

A driver whose DTCI is small is not necessarily harmless: it may be holding
capacity without taking the system down. That is what the lost-capacity
columns measure.

=== See it, not just read it

The **Charts** tab paints the same figures the report uses. Each chart has a
one-sentence caption you can quote, values on hover, click-to-locate, and
PNG/SVG/CSV export. **Target** draws an availability target on the outcome,
chance, time and year charts; **Capacity target** does the same on the
capacity year chart. The dot plots mark the median and quartiles, and a
chart over time can be dragged (or Ctrl+wheeled) to zoom its time axis,
with a double-click to restore the whole run.

The list on the left groups the charts by the question they answer. Click a
group's heading to see its charts as small pictures, each with a line on
what it answers; **All charts**, above the first group, shows every group
on one long page under its own heading, so you can scroll the lot and open
the one you want. The search box narrows both. The set includes:

* the run-to-run dot plot and **Chance of reaching a value**: the share of
  runs on the horizontal axis and the value they reached on the vertical, so
  "9 runs in 10 reached at least 99.2 %" reads straight off the curve. Move
  the pointer over it for a cross-hair that says exactly that;
* the downtime Pareto with cause stacks. Each cause has its own colour and
  pattern so the stack still reads in greyscale; the key above the chart
  names them, and the whisker on each bar is ± 2 standard errors. The
  colours come from **Preferences ▸ Appearance ▸ Chart palette**: *Muted*
  (the default, with a softer repair red), *Raptor classic*, *Colour-blind
  (Okabe–Ito)* and *High contrast*; the choice applies to the screen, the
  PDF report and every exported image;
* the availability ladder: inherent (repair only), achieved (plus planned
  maintenance), operational (plus logistics, spares and crews);
* the outage-duration histogram on a log scale;
* frequency against duration, one bubble per element;
* the downtime treemap, the outage anatomy (what an outage *looks* like,
  step by step) and the run-to-run ribbon (every trial as one row, green up
  and red down);
* the hierarchy views: a scorecard and Pareto at one level, a nested
  treemap or concentric sunburst (one switchable nested view), cumulative
  overlays and small multiples, cause and phase heatmaps, an outage state
  ribbon, and a change chart against another stored run. **Scope**
  follows the canvas level or pins one hierarchy; **Depth** shows the top
  level, one numbered level or every level, and inside a chosen hierarchy
  counts down from it (it starts at every level; "1 level down" lists only its own contents, deeper
  levels open its sub-hierarchies); on the downtime, lost-capacity and cost
  treemaps it gathers anything deeper into one cell per hierarchy;
  **Compare** picks up to four
  sibling branches; **Baseline** stores the comparison run;
* convergence: the running mean with its ± 2 standard-error band;
* year-by-year availability when the run covers whole years (hours models);
With capacity analysis on, three more charts answer "who loses the
capacity", which is not the same question as "who is down":

* **Who loses the capacity**: each element's share of the lost flow beside
  its share of the downtime, in the same order, so an element that rarely
  stops the system but often throttles it stands out;
* **Downtime against lost capacity**: one point per element, both shares;
* **Lost capacity by cause**: from the flow the model could deliver down to
  what it did deliver, one step per cause;
* **Lost capacity treemap**: area = share of the lost flow, colour = the
  element's main downtime cause;
* **Lost capacity by hierarchy and cause** (Sankey): the flow from what
  could be delivered, through each hierarchy, to the causes that lost it;
* **Capacity delivered year by year**: capacity-weighted availability for
  each year, with the spread across runs. A year can be 100 % available and
  still deliver only 96 % of the flow.

With cost analysis on, **Where the money goes** ranks the elements by mean
cost per run, and the **Cost treemap** shows the same money as areas,
coloured by its largest part (purchase, operating, spares or disposal).
Spare pools are cells of their own, so the treemap is also the spares
picture: a large amber cell is an element whose cost is mostly spares.

The lost flow is split among the elements down at the time
(`--capacity-rule proportional` by default), and the split adds up to the
engine's own lost flow. The engine writes capacity times to six decimals, so
a flow change can land a millionth of an hour from the event that caused it;
such a sliver is charged to the elements of the neighbouring outage rather
than left unexplained.

Capacity-weighted availability for one period is the flow delivered in it
divided by the flow the model could deliver over the same time:

....
capacity-weighted availability = flow delivered in the period
                                 / (flow generated x period length)
....

When the run is a whole number of years, the average of the yearly values
equals the engine's own capacity-weighted availability for the run.

Two canvas controls tie the views together. **Show on Canvas** chooses one
result measure (weak link, capacity, cost, spares or importance) and paints
it over the diagram; **View ▸ Focus** dims everything except the selection,
so a large diagram keeps its topology but shows only what matters.
Selecting a block on the canvas also marks its row in the Drivers view, and
clicking a chart or driver locates the block on the canvas.

The command line writes one chart as SVG, which is what a report embeds:

[source,bash]
----
raptor explain VanFlat.rbds --chart downtime-pareto --chart-svg downtime.svg
raptor explain --list-charts
----

MCP clients call `run_chart(run_id, chart="downtime-pareto")` and receive the
same specification plus the SVG. The capacity charts are `lost-capacity-pareto`,
`capacity-vs-downtime`, `capacity-waterfall`, `lost-capacity-treemap` and
`annual-capacity-fan`; the cost charts are `cost-pareto` and `cost-treemap`.

The numbers behind the charts export as tables. In the GUI they are in
**File ▸ Export ▸ Export Tables…** (or the Export Tables… button in the data tables); from the command line, run the model and ask for
the attribution tables too:

[source,bash]
----
raptor tables Water2.rbds --run --drivers --format xlsx -o out/
----

That adds `results.downtime_drivers`, `results.downtime_causes`,
`results.phase_downtime` (phased models),
`results.outage_durations`, `results.lost_capacity` (by element),
`results.lost_capacity_causes`, `results.period_availability`,
`results.period_capacity` and `results.period_runs` (one row per run and
year, for your own statistics). MCP clients get the same tables through
`export_tables`, and `annual_availability(run_id, include_runs=True)` returns
the year-by-year figures with capacity.

=== Stop when the answer is precise enough

A fixed run count is a guess. Ask for a relative precision instead:

[source,bash]
----
raptor run VanFlat.rbds --precision 5%
raptor run VanFlat.rbds --precision 5% --precision-metric system.mdt --max-trials 5000
----

The runner grows the batch, reads the per-run values, and stops when the
relative half-width of the watched metric meets the target: half-width ≤
r/(1+r) × mean for a target r, using Student's *t* at the chosen confidence
(95 % unless `--precision-confidence` says otherwise). Availability and
reliability are watched as the part lost (1 − value), so 5 % means 5 % of
the downtime, not of the uptime; a time such as MDT is watched as itself. Batches are
re-run with the same seed, so the final batch is exactly the first *n*
trials of a fixed *n*-trial run; the seed table is untouched. The result
carries the reached interval, the target, the trial count and the pass
history.

In MCP, pass `precision={"relative": 0.05}` to `simulate`. In the
application, *Simulate ▸ Trials to Precision…* (or *Precision…* beside
Trials in the Run panel) runs the same passes on a copy, lists each one,
and sets the next Run to the trial count it reached.

=== What if: compare against the model you have

A scenario is this model plus a short list of `PATH=VALUE` changes. It is
never a second file, and the open model is never modified:

[source,bash]
----
raptor whatif VanFlat.rbds \
  --change 'block:Fuel_Pump.repair_params=2,0.25,0' \
  --name 'Faster fuel pump repair' -n 200
----

The base and the scenario run with the same seed, so trial *i* is paired;
the table reports the scenario value, the paired difference with its
standard error and `P(better)`, the chance that the scenario really is
better and the difference is not noise. Halving the fuel pump's repair time
gains about 0.4 points of availability, with a standard error under 0.05.
Pairing can narrow the difference's uncertainty, but expect little: the
random streams run on from one trial into the next, as in Raptor 7, so once
the change moves one event the two runs draw different numbers. On the
book's models it cuts a few per cent of the variance, sometimes none. It
never biases the comparison, the standard error comes from the paired
differences either way, and the `Pairing cut the variance by` line says
what was gained.

Use the same seed, the same trial count and the same number of cores when
you compare two runs by hand; otherwise you are reading noise. The numbers
depend on the cores (`-j`): one core and several draw different streams, so
the header says how many were used. The What If window (Analyse ▸ What If)
uses the cores chosen in the Run panel, so it can differ from a command-line
`whatif`, which uses one unless you give `-j`.

A change can have no effect at all, such as a repair time on a block that is
never repaired. Every trial is then identical to Base: the result says "no
effect" and the window does not offer Apply. Besides block, node, event,
hierarchy, link, system and rate paths, a change can set a spare pool's
stock or a crew pool's size: `pool:Spares.stock=3`, `resource:Crew.units=2`.

=== Which inputs matter

The tornado varies each candidate input at a low and a high value, with the
same seed as Base, and ranks the paired swings:

[source,bash]
----
raptor sensitivity VanFlat.rbds --top 8 -n 100
----

Candidates come from block lives and repair means, PM intervals, finite
spare stock and crew counts. Only the first `--top` of them are screened
(10 by default): after a run with downtime attribution, the elements that
cause the most downtime come first; without one, the blocks down for the
largest share of their own time. The output says how many of the inputs
were screened; raise `--top` to screen the rest. The Sensitivity window
(Analyse ▸ Sensitivity) does the same, using the last run's attribution. A swing whose interval contains zero is drawn
as "not distinguishable" rather than promoted. This is a screening view: it
shows each input alone, so it cannot show interactions.

=== How many spares

The spare optimiser starts from a Poisson backorder model, orders one-unit
increments by backorder reduction per unit cost, and simulates that path,
every point with the same seed:

[source,bash]
----
raptor optimise spares DC1.rbds --target 'system.ao>=0.999' --budget 30
raptor optimise spares DC1.rbds --target 'system.ao>=0.999' --apply
----

The model needs a finite spare pool that its blocks draw on; VanFlat keeps
no pool, so the data-centre model is used here. It holds three cooling-unit
spares today, and two are enough:

----
Base: 0.99952 (lower 0.99931), holding cost 3
   CRAC_Spares 0                    0.99935 (lower 0.9989)  cost 0
   CRAC_Spares 1                    0.99903 (lower 0.99831)  cost 1
 * CRAC_Spares 2                    0.99948 (lower 0.9992)  cost 2
   CRAC_Spares 3                    0.99952 (lower 0.99931)  cost 3

Recommended: CRAC_Spares 2 — availability 99.95 % (lower bound 99.92 %)
against a target of 99.9 %; ... That is fewer than the 3 held today: the
extra stock buys no measurable availability at this run count.
----

Look at the first two rows: no spares measured *better* than one. That is
noise, not a property of the model: at this run count the differences
between 0, 1 and 2 spares are about the size of their standard errors.
The lower bound is what keeps a lucky row from being recommended (no
spares has the mean but not the lower bound), and more runs (`-n`) would
separate them.

A point counts as meeting the target only when the cautious end of its
confidence interval does: the *lower* bound for availability, the *upper*
bound for a measure where less is better, such as mean downtime. The lead
time each part's demand is counted over comes from the pool: the
emergency-order time when one is set, the normal order time, the regular
delivery interval, or else the whole run. The command prints every evaluated point and recommends the cheapest
one that qualifies; `--apply` writes the stocks into the model, and leaving
it out changes nothing. If every spare cost is the default 1, the result
minimises the number held rather than money, and the caption says so.

=== From a finding to a tested change

The drivers say where the downtime comes from; a decision needs the change,
what it buys and what it costs. `raptor recommend` does all three in one
step. It runs the model with attribution, takes the blocks that cause the
most downtime, picks one lever for each from the cause behind its outages,
and tests every change against Base with paired runs:

[source,bash]
----
raptor recommend VanFlat.rbds --top 3 -n 200
----

The levers are fixed, stated steps:

[cols="1,2",options="header"]
|===
| Main cause of the block's outages | Change tested
| Hands-on repair | the repair law's mean halved, its shape kept
| Logistics delay | the delays before and after repair halved
| Waiting for a spare, or never repaired | one more spare in its pool (or its own stock)
| Waiting for people or equipment | one more unit of its crew
| Planned maintenance | the PM interval doubled
| (the largest driver only) | a part that lasts twice as long
|===

Each result prints the `PATH=VALUE` change, so `raptor set` or `raptor
whatif` can take it as it stands, the paired availability gain with its
standard error and `P(better)`, the downtime saved per run, and the cost.
A spare or crew carries the unit cost stored in the model; with cost
analysis on, the change in the run's grand total is shown too. A faster
repair or a better part has no price in the model, so its cost is reported
as unknown, never as zero.

The verdict says what was measured, not whether the change is worth its
price:

* *clearly helps*: the gain is real and material. Real means `P(better)`
  clears 95 % shared across all the changes tested together (with five
  changes, each needs 99 %), so testing several at once does not let one
  through by luck. Material means it removes at least 5 % of Base's
  downtime; `--min-gain` sets another bar in availability points.
* *helps a little*: real, but smaller than that.
* *may help; run more trials*, *no measurable gain*, *makes it worse*.

No verdict weighs cost. A change that clearly helps can still cost more
than it is worth: each result says what is left to weigh.

The step size is not an optimum. Recommend finds the lever that matters;
`raptor optimise` sizes it (Analyse ▸ Spares, Maintenance and Crews in the
application). In the application the same tool is Analyse ▸ Recommend, where Apply writes the chosen change into the model as
one undo step. An AI assistant calls `recommend_changes`.

=== The rule that keeps this honest

Attribution describes the design you simulated. Importance and what-if
answer what a change would achieve. Never use a DTCI ranking as if it were
a what-if result: the element that causes the most downtime now is not
always the one whose fix buys the most.

=== Keep the parts you reuse

The **Part Library** tab beside the Explorer keeps two kinds of entry:

* a *part type* is one element's data (failure and repair, logistics,
  spares, maintenance, cost) without its name or place. Apply it to other
  elements of the same kind; a later change to the part can be synced, and
  fields you edited by hand stay as overrides.
* an *assembly* is a group of elements kept with its links: a hierarchy with
  everything inside it, a node with the blocks around it, a set of events.
  Insert it, or drag it onto the canvas, and you get a fresh copy with new
  names; links to elements outside the group are dropped, and spare pools or
  resources the model does not have are reset, exactly as a paste from
  another model resets them.

Select the elements and press **Save selection…**: the dialog offers an
assembly, or a part type when the selection is a single element. The command
line and MCP do the same:

[source,bash]
----
raptor library add parts.rbdlib VanFlat.rbds --assembly Tire_FL,Tire_FR,Tire_RL,Tire_RR,Tires_vote --name "Tyre set"
raptor library insert VanFlat.rbds --library parts.rbdlib --part "Tyre set" --in-place
----

MCP clients call `save_assembly` and `insert_assembly`.
