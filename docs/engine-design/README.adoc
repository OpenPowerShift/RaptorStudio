= Engine design: algorithm pages
:toc: macro

One page per group of engine procedures: a curated set of the algorithms a reader must understand, each with a picture. They explain _how the port is built and why_, naming the Raptor 7 procedure each part reproduces; the golden captures under `tests/golden/` are the evidence that the port matches.

toc::[]

== Reading order for a newcomer

. xref:decisions.adoc[The design decisions]: the choices the code does not explain by itself.
. The algorithm page below for the area you will touch.

== Template for a page

Each page has these sections, in this order. Leave a section out only if it would be empty.

. *Purpose.* What the component does, in two or three sentences, for someone who has never seen it.
. *Source anchors.* A table mapping each source method to the Python that ports it.
. *Structure.* A flowchart of the procedure.
. *States.* A state diagram, if the component has states.
. *Interactions.* A sequence diagram of one representative change as it moves between components. This is the view newcomers most need.
. *State it owns.* What persists between waits, grouped by concern.
. *Port-only devices and deliberate deviations.* Everything that exists because the port is shaped differently from source, with the reason for each.
. *Invariants.* What must always hold, and where it is checked.
. *Tests and fixtures.* What pins this behaviour down.

== Rules that keep pages true

* *Pages are AsciiDoc; diagrams are `[mermaid]` blocks in the page*, never images or binary documents. A diagram changes in the same PR as the code it describes. GitHub shows a `[mermaid]` block as its source, which is readable on its own. Asciidoctor with the `asciidoctor-diagram` extension renders it as a diagram.
* *Name code in backticks* exactly as written (`BlockProcess._repair`, `InterruptReason.OBPM`). `tests/unit/test_engine_design_docs.py` checks that every `BlockProcess.<member>` and engine `<module>.<name>` a page names still exists. A rename that strands a page then fails CI in that PR.
* *Explain; don't transcribe.* A page says what the code is for and how the parts fit together. Line-by-line detail belongs in docstrings and comments, next to the code.
* *Update the page in the PR that changes the design*, as you would a test.
