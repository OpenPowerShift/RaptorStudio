== Purpose

A block that fails needs a *spare* (from an infinite supply, its own Custom stock, or a shared spare pool) and possibly *resources* (people or tools from a resource pool) before its repair can start. Pools are FIFO queues that give and take back; spare pools are also replenished in the background by routine, emergency and stock-level ordering.

== Structure

`Give` is two-stage: a request that can be met is granted at once, otherwise the block parks (`REPAIR_POOL_SPARE`, `REPAIR_RESOURCE` in the block state machine); a `TakeBack` or arrival grants the head of the queue by interrupting it with `Pool_Available` and a token saying whether the grant is for a repair or a PM.

[mermaid]
....
flowchart LR
    fail["block fails"] --> chk["check stock;<br/>maybe order a spare (ESO)"]
    chk --> req["request a spare"]
    req -->|in stock| have["spare in hand"]
    req -->|empty| wait["RepHold: Waiting_for_Spare"]
    wait -->|"arrival / take-back"| have
    have --> res["request resources"]
    res --> rep["repair"]
    rep --> back["resources taken back;<br/>waiters woken in FIFO order"]
....

== Port-only devices and deliberate deviations

* Pool processes are in the scheduler's front tier: at one instant a pool's own records run before ordinary ones.
* A block asking for a resource count other than one uses none (`NumRes` other than 1; source's check is `numDiffRes=1`); a ColdPool or Resource `SpType` string loads as "no sparing".
* Dependent blocks run the ordinary process, so they take spares and resources exactly as other blocks do.
