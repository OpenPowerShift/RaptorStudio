== Purpose

*Events* are one-shot random outcomes (Success, Failure, Armed) that sit in the diagram like blocks. *Phases* divide a run into stretches with their own duration, mission flag, and per-element settings: a block or node can be Active, Cut (out of the diagram) or Linked (bypassed) in each, with a stress or k value. A phase change re-applies every phased element and can begin or end a *mission*.

== Structure

[mermaid]
....
flowchart TD
    clock["phase clock wakes"] --> log["log Begin_phase"]
    log --> conduct["conduct_phase_change<br/>(PhaseChangeInProgress = true)"]
    conduct --> cls["classify each phased element:<br/>Cut / Link / Active, stress change"]
    cls --> groups["apply groups: improve, stress, degrade<br/>(reversed when the system is Red)"]
    groups --> defer["release deferred PMs (NonMission)"]
    defer --> cold["CheckColds"]
    cold --> mission["begin a mission if the phase is one"]
    mission --> done["PhaseChangeInProgress = false,<br/>release pmSyncTrigger"]
....

While a phase change is in progress a pmMisDefer block whose PM trigger fires waits for it to end, so the PM is judged against the new mission status (`pmSyncTrigger`, `PmMisDeferBoundaryProbe`).

== Port-only devices and deliberate deviations

* The zero-time hops are ported literally (5 per block or event, 1 per node, 5 for the Green/Yellow degrade loop). One extra hop before the deferred-PM release is a heuristic (its comment says so) that keeps a released PM's line after the cold survey's.
* A phased cold node reconfigures through `ColdChangeGroup`, not inline.
* Interim Costs flips the order of the phase clock and the trigger draws at t=0 (see the kickoff page).

== Ordering at a boundary

Because the body is a TELL, a block failing at exactly a phase boundary logs `Failed`, then `Begin_phase`, then `RepHold` (`PhaseFailTieProbe`), and a pmMisDefer block whose PM clock expires there hops, sees the change in progress and waits on `pmSyncTrigger` (`PmMisDeferTimerProbe`). Both were traced in real.
